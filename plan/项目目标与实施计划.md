# 小组协作工具箱项目目标与实施计划

## 1 项目定位

本项目拟开发一个面向课程小组、比赛团队和小型项目组的 Web 应用。系统以小组管理和任务协作为核心，同时提供共享文件库、临时文件中转和跨设备内容传递工具，使成员能够在同一平台完成组队、分工、提交、审核、归档和文件传递。

项目需要形成以下完整工作闭环：

> 创建小组 → 邀请成员 → 分配权限 → 发布任务 → 成员提交成果 → 负责人审核 → 成果归档 → 小组共享或临时传递

临时文件中转和跨设备工具不能成为孤立功能。用户应当能够把这些工具中的文件直接用于任务提交，或保存到有权访问的小组文件库。

## 2 总体完成目标

项目完成时，应达到以下目标：

- 用户能够通过账号使用系统，并在电脑和手机浏览器中访问主要功能。
- 用户能够创建或加入小组，不同小组的数据相互独立。
- 组长能够管理成员，并为成员分配任务管理、文件管理和公告管理等权限。
- 小组能够完成任务发布、进度更新、成果提交、审核反馈和成果归档的全过程。
- 小组成员能够在共享文件库中上传、查找、预览和下载资料。
- 用户能够通过取件码或二维码临时传递文件，并控制分享有效期。
- 用户能够通过个人设备空间在不同设备间传递文字、链接和文件。
- 用户能够从个人工作台快速查看待办任务、未读通知和常用工具。
- 系统对关键操作给出明确结果，不出现无提示失败、重复提交或越权操作。

## 3 用户角色与权限目标

### 3.1 普通用户

普通用户是系统的基础身份。用户可以注册和登录账号、修改个人资料、创建小组、申请加入小组，以及使用个人临时中转和跨设备工具。

同一个用户可以加入多个小组，但用户在一个小组中获得的权限不能自动带到另一个小组。

### 3.2 普通成员

用户加入小组后成为普通成员。普通成员至少可以查看小组成员、公告、任务和允许访问的共享文件，可以更新自己的任务进度、提交任务成果，并参与小组讨论。

普通成员不能自行修改他人权限，也不能执行尚未获得授权的小组管理操作。

### 3.3 组长

每个小组有一名组长。组长拥有本组的完整管理权限，包括管理成员、审核入组申请、授予或撤销权限、发布任务、审核成果、管理文件和公告，以及查看小组整体进度。

组长可以把组长身份转让给其他成员。组长身份只影响当前小组，不能访问成员的个人设备空间或个人临时文件。

### 3.4 授权成员

组长可以按照工作需要，为成员分别授予以下权限：

- 任务管理：发布、修改和取消任务。
- 成果审核：审核任务提交并反馈修改意见。
- 文件管理：管理共享文件和归档任务成果。
- 公告管理：发布、修改和撤下小组公告。
- 成员管理：邀请成员和审核入组申请。该权限可作为完善功能实现。

授权应按功能分别设置。拥有一种权限的成员不自动拥有其他管理权限，也不能继续向他人转授权限。

## 4 功能模块目标

### 4.1 账号与个人资料

必须完成：

- 用户可使用账号和密码注册、登录和退出。
- 注册时检查账号是否重复，登录失败时给出明确提示。
- 登录用户可查看和修改姓名等基础资料。
- 未登录用户只能访问注册、登录和公开取件页面。
- 系统能够保持登录状态，并保护需要登录才能使用的页面和接口。

验收结果：新用户可以完成注册和登录；刷新页面后仍能识别当前用户；退出后不能继续访问个人和小组内容。

### 4.2 小组与成员管理

必须完成：

- 用户可创建小组并填写名称和简介，创建者自动成为组长。
- 组长可生成邀请信息，其他用户可据此申请加入小组。
- 组长可同意或拒绝入组申请。
- 用户可查看自己加入的小组，并在不同小组之间切换。
- 组长可查看和移除成员，成员可主动退出小组。
- 组长可将组长身份转让给本组其他成员。

完善功能：

- 邀请可设置有效期并由发布者提前取消。
- 被移除或退出的成员立即失去小组内容访问权限。
- 成员退出后，其已经提交的任务成果仍保留在任务记录中。

验收结果：至少可以建立两个数据相互独立的小组；普通成员无法进入未加入的小组；组长转让后，新组长获得管理能力，原组长按普通成员处理。

### 4.3 权限管理

必须完成：

- 组长可查看每位成员当前拥有的权限。
- 组长可授予或撤销任务管理、成果审核、文件管理和公告管理权限。
- 前端根据权限显示可用操作，后端也必须验证权限。
- 权限撤销后，成员再次执行相关操作时应被拒绝。
- 普通成员不能修改本人或他人的权限。

验收结果：为成员增加权限后，该成员可以执行对应操作；撤销权限后，即使直接调用接口也不能继续执行。

### 4.4 任务管理

必须完成：

- 组长或有权限的成员可创建任务。
- 任务至少包含标题、说明、负责人或执行成员、截止时间和当前状态。
- 任务管理者可修改或取消任务。
- 成员可查看与自己有关的任务，并按未开始、进行中、待审核、已完成等状态筛选。
- 执行成员可更新自己的任务进度。
- 任务页面可附带参考文件或引用共享文件。

任务的基本状态建议为：

1. 未开始：任务已分配，成员尚未开始处理。
2. 进行中：成员已经开始工作。
3. 待审核：成员已提交成果，等待审核。
4. 需修改：审核者退回成果并给出意见。
5. 已完成：成果已经审核通过。
6. 已取消：任务被任务管理者取消。

验收结果：任务从创建、执行、提交到完成能够完整流转；没有管理权限的成员不能修改或取消任务。

### 4.5 成果提交与审核

必须完成：

- 执行成员可提交文字说明、链接或文件作为任务成果。
- 系统记录提交者和提交时间。
- 组长或有审核权限的成员可查看任务提交情况。
- 审核者可通过提交，或退回并填写修改意见。
- 退回后，成员可以根据意见重新提交。
- 组长可查看每个任务和成员的完成情况。

完善功能：

- 保留同一成员的多次提交记录。
- 支持选择多个成员成果批量打包下载。
- 对超过截止时间的提交显示逾期标记。

验收结果：成员提交成果后，审核者能够看到正确的文件和提交信息；退回后成员可以再次提交；通过后任务显示已完成。

### 4.6 小组讨论与公告

必须完成：

- 成员可在小组讨论区发送文字消息。
- 成员可在任务详情下留言，使讨论与具体任务关联。
- 组长或有权限的成员可发布、修改和撤下公告。
- 所有成员可查看当前小组公告。

完善功能：

- 讨论中支持引用共享文件或上传图片。
- 公告可置顶，成员能够区分普通公告和重要公告。

验收结果：不同小组的讨论和公告相互隔离；普通成员不能发布或修改公告。

### 4.7 通知

必须完成：

- 发布任务时通知相关执行成员。
- 任务即将到期时向执行成员显示提醒。
- 成果通过或退回时通知提交成员。
- 发布公告时通知本组成员。
- 用户可查看未读通知数量，并点击通知进入对应内容。

完善功能：

- 用户在一个设备上阅读通知后，其他设备同步已读状态。
- 用户可按通知类型筛选历史通知。

验收结果：任务分配、审核结果和公告至少能产生站内通知，通知跳转目标正确。

### 4.8 小组共享文件库

必须完成：

- 有权限的成员可上传文件到当前小组文件库。
- 成员可查看和下载有权访问的共享文件。
- 文件至少记录名称、大小、上传者、上传时间和所属小组。
- 文件可按名称搜索，并可按分类查看。
- 系统支持对常见图片、纯文本或 PDF 中的一部分类型进行在线预览。
- 有权限的成员可删除或调整文件分类。
- 审核通过的任务成果可归档到共享文件库。

完善功能：

- 支持上传文件的新版本，并查看历史版本。
- 支持选择多个文件打包下载。
- 显示小组已使用的存储空间。

验收结果：成员只能看到所在小组的共享文件；任务成果归档后可以在文件库中找到并下载。

### 4.9 临时文件中转

必须完成：

- 登录用户可上传临时文件。
- 上传成功后生成唯一取件码或取件链接。
- 系统可以根据取件码找到并下载对应文件。
- 用户可设置文件有效期。
- 文件所有者可在到期前取消分享。
- 用户可查看本人创建的临时分享及其当前状态。

完善功能：

- 根据取件链接生成二维码，便于手机扫码领取。
- 记录文件被领取的次数。
- 到期后自动禁止下载并清理临时文件。

验收结果：用户上传文件后，能够在另一个浏览器通过取件码下载；取消或到期后，同一取件码不再可用。

### 4.10 跨设备内容传递

必须完成：

- 用户可在电脑和手机浏览器登录同一个账号。
- 用户可将文字、链接和文件主动发送到“我的设备”空间。
- 同一账号的其他设备可查看、复制或下载这些内容。
- “我的设备”空间仅账号本人可见，不属于任何小组。
- 用户可删除不再需要的跨设备记录。

完善功能：

- 页面根据手机和电脑屏幕自动调整布局。
- 新内容到达时显示提示。
- 显示内容来源设备和发送时间。

验收结果：在电脑端发送一段文字或文件后，手机端刷新即可看到；其他账号和小组管理员均不可访问。

### 4.11 工具与协作功能衔接

这是本项目区别于普通小组管理系统的核心目标，必须完成以下衔接：

- 用户可选择临时中转文件作为本人的任务成果，无需再次从本地上传。
- 用户可选择“我的设备”中的文件作为本人的任务成果。
- 用户拥有文件上传权限时，可将临时中转或“我的设备”文件保存到当前小组文件库。
- 任务审核通过后，有权限的成员可将成果归档到共享文件库。
- 文件从个人空间进入小组空间前，应明确显示目标小组，避免误传。

验收结果：至少完整演示一次“手机发送文件到我的设备 → 电脑端选择该文件提交任务 → 组长审核 → 归档到小组文件库”的过程。

### 4.12 个人工作台

必须完成：

- 显示用户所在的小组及快速切换入口。
- 显示待完成、待修改和即将截止的任务。
- 显示未读通知数量。
- 提供共享文件、临时中转和“我的设备”等常用工具入口。

完善功能：

- 组长可看到当前小组任务总数、完成数量和待审核数量。
- 用户可按小组查看个人任务完成情况。

验收结果：用户登录后无需逐个进入模块，就能知道当前最需要处理的任务和通知。

## 5 主要页面目标

第一版至少需要完成以下页面：

| 页面 | 主要内容 |
| --- | --- |
| 注册与登录 | 注册账号、登录和错误提示 |
| 个人工作台 | 小组入口、待办任务、通知和工具入口 |
| 小组主页 | 小组信息、公告、成员和近期任务 |
| 成员与权限 | 成员列表、入组申请和权限设置 |
| 任务列表 | 任务筛选、状态和截止时间 |
| 任务详情 | 任务说明、留言、成果提交和审核 |
| 共享文件库 | 文件上传、搜索、分类、预览和下载 |
| 临时文件中转 | 上传、生成取件码、查看与取消分享 |
| 公开取件 | 输入取件码并下载有效文件 |
| 我的设备 | 发送、查看、复制和删除跨设备内容 |
| 通知中心 | 未读与历史通知、跳转到相关内容 |

## 6 核心数据目标

系统至少需要保存以下数据对象：

- 用户：账号、密码摘要、姓名和创建时间。
- 小组：名称、简介、组长和创建时间。
- 小组成员：用户、小组、成员身份和加入时间。
- 成员权限：成员在指定小组内拥有的各项权限。
- 入组申请或邀请：目标小组、申请人、状态和时间。
- 任务：所属小组、标题、说明、执行成员、截止时间和状态。
- 任务提交：所属任务、提交者、文字、链接、文件和审核状态。
- 审核记录：审核人、结果、修改意见和审核时间。
- 公告与讨论：所属小组或任务、发布者、内容和时间。
- 通知：接收用户、通知类型、关联对象和已读状态。
- 共享文件：所属小组、文件信息、上传者和分类。
- 临时文件：文件所有者、取件码、有效期和分享状态。
- 跨设备内容：所属用户、内容类型、内容和发送时间。

文件可以存放在本地文件目录或对象存储中，数据库只保存文件位置及相关信息。用户密码必须保存加密后的摘要，不能保存明文密码。

## 7 非功能目标

### 7.1 安全与权限

- 所有小组数据查询都要检查当前用户是否属于该小组。
- 所有管理操作都要在服务端验证权限，不能只依靠前端隐藏按钮。
- 私人跨设备内容只能由所属用户访问。
- 上传文件应限制大小，并避免使用用户提交的原始文件名直接作为服务器路径。

### 7.2 易用性

- 主要操作应提供成功或失败提示。
- 上传文件时应显示上传状态。
- 删除、取消任务、移除成员等重要操作应要求用户确认。
- 状态名称和按钮文字在不同页面保持一致。

### 7.3 兼容性

- 系统以 Web 应用为主，支持常见桌面浏览器。
- 核心页面应能在手机浏览器中正常操作。
- 中文内容、文件名和搜索应正常显示。

### 7.4 可维护性

- 前端页面、业务逻辑和数据访问应适当分层。
- 权限判断、文件上传和通知创建应封装为可复用逻辑。
- 数据库结构和接口命名应保持一致，并为重要接口留下简要说明。

## 8 开发阶段与里程碑

### 第一阶段 项目基础

- [ ] 确定前端、后端、数据库和文件存储方案。
- [ ] 建立项目目录和版本管理仓库。
- [ ] 完成数据库初步设计。
- [ ] 完成注册、登录、退出和登录状态验证。
- [ ] 实现账号唯一性检查、密码摘要存储和多设备登录会话。
- [ ] 设计统一的文件记录与物理文件存储方式，禁止直接使用原文件名作为存储路径。
- [ ] 完成基础页面布局和路由。

阶段验收：用户可完成注册登录，并进入空的个人工作台。

### 第二阶段 小组与权限

- [ ] 完成小组创建和小组切换。
- [ ] 完成邀请、入组申请和成员管理。
- [ ] 完成组长身份和分项权限管理。
- [ ] 在前后端接入权限检查。
- [ ] 验证所有小组数据查询均受成员身份和小组范围限制。
- [ ] 处理组长转让、成员离组和历史数据保留规则。

阶段验收：组长能够建立小组、加入成员并授予权限；普通成员不能越权管理小组。

### 第三阶段 任务闭环

- [ ] 完成任务创建、修改、取消和分配。
- [ ] 完成成员任务列表和进度更新。
- [ ] 完成文字、链接和文件成果提交。
- [ ] 完成审核通过、退回和修改意见。
- [ ] 使用统一状态机限制任务状态变化，并区分提交成果与审核完成。
- [ ] 明确多人任务的提交与完成规则，保存重新提交的版本记录。
- [ ] 对重复点击和网络重试进行防重复处理。
- [ ] 完成小组任务进度统计。

阶段验收：从任务发布到审核完成的完整流程可以运行。

### 第四阶段 小组协作

- [ ] 完成小组讨论和任务留言。
- [ ] 完成公告发布和查看。
- [ ] 完成任务、审核和公告站内通知。
- [ ] 防止同一业务事件产生重复通知，并处理通知目标失效的情况。
- [ ] 完成共享文件上传、搜索、下载和归档。
- [ ] 确保搜索和文件下载按照当前用户权限过滤结果。

阶段验收：小组成员能够围绕任务沟通，并将完成成果归档到共享文件库。

### 第五阶段 文件工具

- [ ] 完成临时文件上传、取件码和下载。
- [ ] 完成有效期、取消分享和分享记录。
- [ ] 使用不可预测且不重复的取件码，限制连续错误尝试和异常下载频率。
- [ ] 完成过期临时文件的状态更新和实际文件清理。
- [ ] 完成“我的设备”文字、链接和文件传递。
- [ ] 验证“我的设备”仅本人可见，组长和其他成员均不能访问。
- [ ] 完成手机端基本适配。

阶段验收：临时取件和同账号跨设备传递均可在两台设备或两个浏览器中演示。

### 第六阶段 功能衔接与交付

- [ ] 将临时文件和跨设备文件接入任务提交。
- [ ] 确保个人或临时文件进入任务后形成独立业务记录，不受原记录删除或过期影响。
- [ ] 将任务成果接入共享文件归档。
- [ ] 完善个人工作台的待办、通知和工具入口。
- [ ] 检查工作台、搜索和统计结果均经过权限过滤。
- [ ] 修复权限、文件和任务流程中的主要问题。
- [ ] 完成关键操作记录、基础备份和异常恢复验证。
- [ ] 准备演示账号、示例小组、任务和测试文件。
- [ ] 编写项目说明、部署说明和课程展示材料。

阶段验收：核心演示流程可以连续完成，数据和权限结果正确。

## 9 优先级与范围控制

### 必须完成的最小可用版本

如果开发时间不足，必须优先保证以下内容：

1. 注册登录。
2. 创建和加入小组。
3. 组长管理成员及权限。
4. 发布任务和查看任务。
5. 提交成果和审核成果。
6. 小组共享文件上传与下载。
7. 临时文件取件码。
8. “我的设备”跨设备传递。
9. 文件工具与任务提交的衔接。

### 应当完成的完善功能

- 公告和站内通知。
- 任务进度统计。
- 文件搜索、分类和基础预览。
- 成果批量下载和归档。
- 手机页面适配。

### 可以后续扩展的功能

- 文件历史版本和回收站。
- 实时聊天和消息推送。
- 在线文档共同编辑。
- 邮件、短信或系统级通知。
- 桌面客户端和自动读取系统剪贴板。
- 多级组织、部门和复杂审批流程。

这些扩展不影响课程项目核心闭环，第一版不应因追求扩展功能而延误主要功能。

AI 功能暂不列入当前版本或确定的后续版本，具体用途、接口成本、数据范围和实现优先级留待后期单独商议。

## 10 测试与验收目标

项目最终至少准备以下测试场景：

1. 用户 A 创建小组，用户 B 申请加入，用户 A 同意申请。
2. 用户 A 给用户 B 授予任务管理权限，用户 B 成功发布任务；撤销后用户 B 无法继续发布。
3. 组长给成员分配任务，成员提交文件，组长退回并填写意见，成员修改后再次提交，组长审核通过。
4. 审核通过的任务成果被归档到小组文件库，其他成员可以搜索并下载。
5. 用户上传临时文件，另一浏览器通过取件码下载；取消分享后无法再次领取。
6. 用户在手机端把文件发送到“我的设备”，在电脑端选择该文件提交任务。
7. 非小组成员尝试访问小组任务和文件时被拒绝。
8. 其他用户尝试访问某人的“我的设备”内容时被拒绝。
9. 用户收到任务、审核结果和公告通知，并能从通知进入对应页面。
10. 网络或上传失败时，页面给出错误提示，不显示虚假的成功结果。

## 11 项目完成标准

满足以下条件时，可认为课程项目主体完成：

- 核心功能可以在实际运行的系统中连续演示。
- 25 条 baseline 用户需求中的主要能力均有对应功能或明确实现结果。
- 普通成员、授权成员和组长的权限边界正确。
- 不同小组之间的数据以及个人空间与小组空间之间的数据不会混淆。
- 任务、提交、审核、归档的状态和结果一致。
- 临时文件中转和跨设备工具至少有一个功能与任务提交真正打通。
- 项目具有可重复运行的启动方法，并准备了必要的数据库初始化或测试数据。
- 项目说明中记录主要功能、使用方法、开发分工、已知限制和后续改进方向。

## 12 建议的演示流程

课程展示时，可以用下面的流程说明整个项目：

1. 组长登录并创建课程小组。
2. 组员通过邀请加入小组。
3. 组长授权一名成员管理文件，并发布一个带截止时间的任务。
4. 组员在手机端将成果文件发送到“我的设备”。
5. 组员在电脑端打开任务，直接选择该文件提交。
6. 组长退回一次并填写修改意见，组员重新提交。
7. 组长审核通过，将成果归档到共享文件库。
8. 文件管理员为需要交给外部人员的文件创建临时取件码。
9. 在未登录窗口输入取件码，完成文件领取。
10. 回到工作台展示任务完成情况、通知和共享文件。

这条演示路线能够同时体现小组管理、权限控制、任务协作、文件管理、临时中转和跨设备使用之间的联系。

## 13 隐形需求与设计约束

本节记录 baseline 功能自然产生、但没有全部写入简要用户需求列表的需求。这些内容应进入详细设计、数据库设计、接口设计和测试计划。除明确标为可选的内容外，实现核心功能时必须遵守这些约束。

### 13.1 账号身份与登录会话

- 用户必须具有系统内唯一的账号标识。显示姓名可以重复，也可以修改，但账号标识不能与其他用户冲突。
- 用户修改显示姓名后，历史记录仍通过用户编号关联，不能因为姓名变化而失去提交者或操作者信息。
- 密码必须保存为安全摘要，数据库和日志中均不得保存明文密码。
- 登录失败时应给出可理解的提示，但不向未登录者暴露过多账号信息。
- 系统需要支持同一账号在电脑和手机同时登录，以满足跨设备使用需求。
- 每个需要登录的页面和接口都要验证登录状态，退出登录后原会话不能继续访问受保护数据。
- 修改密码、主动退出指定设备和查看登录设备可作为完善功能；实现时应以独立会话记录为基础。
- 账号注销不是当前版本的核心功能。若后续加入，需要先定义小组归属、历史提交和共享文件如何保留。

### 13.2 小组隔离与成员生命周期

- 小组是任务、公告、讨论、成员权限和共享文件的数据隔离边界。
- 用户访问任意小组数据时，系统都要检查其当前是否属于该小组，不能只根据任务编号或文件编号返回内容。
- 同一用户可加入多个小组，但其身份和权限必须分别保存，不能跨小组继承。
- 每个小组在正常使用状态下只能有一名组长，组长转让必须整体完成，不能出现两个组长或没有组长的中间状态。
- 组长不能像普通成员一样直接退出。退出前必须转让组长身份，或者按规定解散小组。
- 成员退出或被移除后，应立即失去小组访问权限，但其历史任务提交、留言、审核和操作记录仍需保留。
- 移除成员后，尚未完成的任务需要提示任务管理者重新分配，不能继续把已离组成员作为有效执行者。
- 邀请和入组申请需要具有明确状态，例如待处理、已同意、已拒绝、已失效，避免同一个申请被重复处理。
- 解散小组属于高风险操作，不列入最小可用版本。若实现，必须说明哪些数据被删除、保留或导出，并要求再次确认。

### 13.3 权限模型与越权防护

- 权限必须同时关联用户和小组，任何权限都不能被理解为全局权限。
- 权限采用分项授权，至少区分任务管理、成果审核、文件管理、公告管理和成员管理。
- 获得业务管理权限的成员不能继续向其他成员转授权限。调整权限原则上只允许组长操作。
- 前端可以根据权限隐藏或禁用按钮，但后端必须对每次管理操作重新检查权限。
- 权限撤销后应立即影响后续操作。已经打开的旧页面、缓存数据或旧链接不能绕过当前权限。
- 文件下载、搜索、批量导出和统计查询同样属于受控操作，不能只保护新增、修改和删除接口。
- 系统应遵循最小权限原则。新成员默认仅获得完成本人任务和查看允许内容所需的基础权限。
- 越权请求应返回统一且明确的错误结果，同时避免在错误信息中泄露目标数据内容。

### 13.4 任务状态与多人协作

- 任务状态必须使用固定状态值和统一状态机，不能允许用户随意输入状态文字。
- 成员提交成果后，任务或个人执行状态进入待审核；提交动作本身不能直接代表任务完成。
- 只有组长或具备成果审核权限的成员可以通过或退回提交。
- 被退回的提交进入需修改状态，成员重新提交后再次进入待审核状态。
- 任务取消后不再接受新提交，但已有提交和审核记录应保留用于查看。
- 超过截止时间和禁止提交是两个不同规则。当前方案允许逾期提交，并对提交显示逾期标记。
- 修改任务标题、说明、截止时间或执行成员后，应记录修改时间，并通知受影响成员。
- 多人任务需要保存每个执行成员的独立状态。建议所有执行成员均通过审核后，任务整体才进入已完成状态。
- 增加或移除执行成员、重新开放修改、退回已通过成果时，系统需要重新计算任务整体状态。
- 执行成员离组后，其历史成果仍保留，未完成部分由任务管理者重新分配。
- 用户重复点击提交、浏览器重试或网络恢复时，系统不能生成重复任务或重复提交版本。

### 13.5 提交版本与审核一致性

- 每次重新提交都应形成新的提交版本，至少记录提交者、提交时间、文字说明、文件和版本序号。
- 审核结果必须关联具体提交版本，不能只关联任务，否则无法判断审核的是哪一次提交。
- 审核过程中如果成员产生了更新版本，应提示审核者重新查看最新版本，避免审核旧内容却通过新内容。
- 已通过成果不能由提交者直接覆盖。需要修改时，应由审核者重新开放提交或产生新的版本。
- 批量下载时要明确选择最新提交还是已审核通过的提交，不能混合未审核和已通过成果。
- 任务进度统计应根据有效的当前状态计算，不能仅根据是否存在上传文件判断任务完成。

### 13.6 文件存储、归属与引用关系

- 数据库中的文件记录和服务器中的物理文件必须保持一致，上传失败不能留下可用的提交记录。
- 实际存储路径应使用系统生成的唯一名称，用户原始文件名只作为显示信息保存，避免同名覆盖和危险路径。
- 每个文件必须明确属于个人临时中转、我的设备、小组文件库、任务参考附件或任务提交成果中的一种业务空间。
- 文件从个人空间进入任务或小组空间时，应形成独立业务记录。原临时文件到期或个人记录被删除后，已提交或已归档的文件不能消失。
- 底层可通过文件哈希复用同一个物理文件，但不同业务空间的权限、状态和生命周期必须分别管理。
- 任务引用共享文件时，需要明确引用的是固定版本还是始终使用最新版本。为保证历史可追溯，任务附件和提交成果应固定到所选版本。
- 文件下载和在线预览必须重新检查当前访问权限，不能依靠不可见的文件地址提供保护。
- 上传时至少限制单个文件大小、允许的文件类型和用户或小组总存储量。
- 在线预览仅支持经过确认的安全类型，其他文件只提供下载。
- 删除数据库记录时应同步处理物理文件；删除物理文件前要确认没有任务、归档或其他业务记录仍在使用。
- 文件打包下载应处理同名文件，避免压缩包中相互覆盖。

### 13.7 临时文件中转

- 取件码必须随机、唯一且难以猜测，不能使用简单连续编号。
- 临时分享至少需要有效、已取消、已过期和已清理等状态。
- 取消分享或到期只能阻止后续领取，不能撤回接收者已经下载到本地的副本。
- 公开取件页面只能访问取件码对应的文件，不能借此查看发送者、所属小组或其他文件信息。
- 对连续错误取件码尝试和异常下载频率进行限制，降低枚举和滥用风险。
- 临时文件到期后，不仅要修改数据库状态，还要通过定时清理删除不再被其他业务引用的物理文件。
- 用户可以查看本人创建的分享、有效期和领取次数，但不应看到接收者无关的隐私信息。
- 若设置“仅本人”或“指定用户领取”，接收者必须登录并核对账号；只有“持码者领取”模式允许直接凭有效取件信息下载。
- 共享文件生成对外取件码时必须检查对外分享权限，普通成员不能通过中转功能绕过小组文件权限。

### 13.8 跨设备个人空间

- “我的设备”是服务器上的个人云端空间，不是两台设备之间的直接连接。
- 其中的内容只能由账号本人访问，组长、授权成员和其他组员均无权查看。
- 系统只接收用户主动发送的文字、链接或文件，不自动读取系统剪贴板。
- 同一账号在其他设备登录后可以查看、复制或下载内容，数据应以服务器状态为准。
- 删除云端记录后，其他设备上的列表应同步消失，但系统无法删除用户已经下载到本地的副本。
- 已经提交到任务或保存到小组文件库的独立副本，不应因个人空间记录删除而消失。
- 个人空间需要设置存储上限和清理策略，避免长期累积文件。
- 第一版可以只支持内容新增、查看、下载和删除，不实现多设备实时共同编辑。
- 如果后续支持跨设备任务草稿，应使用更新时间或版本号识别冲突，不能静默覆盖较新的内容。

### 13.9 讨论、公告与通知

- 第一版讨论功能采用持久化留言即可，不要求实现实时聊天或在线状态。
- 小组讨论和任务留言必须属于明确的小组或任务，查询时遵守小组权限。
- 成员可删除本人留言，组长可处理不当内容；若留言已产生回复，可显示“该留言已删除”以保留上下文。
- 公告的发布、修改和撤下需要记录操作者和时间。
- 任务分配、审核结果、公告和截止提醒等事件应产生站内通知。
- 同一个业务事件不能因为接口重试产生多条重复通知，通知应关联任务、公告或审核记录等来源对象。
- 用户点击历史通知时，如果目标已删除或用户已失去权限，应显示内容不存在或无权访问，而不是返回原内容。
- 已读状态属于用户个人状态。同一账号在一台设备标记已读后，其他设备应读取相同状态。

### 13.10 工作台、统计与搜索

- 个人工作台的数据来自多个小组和个人工具，所有汇总结果必须按当前登录用户的权限过滤。
- 成员被移除或权限被撤销后，工作台不能继续显示失效的小组内容或管理入口。
- 工作台应优先展示待完成、需修改、待审核和即将截止的事项，避免只显示总数量而不能操作。
- 任务完成比例需要统一计算口径，明确取消任务是否计入总数、多人任务何时算完成。
- 搜索结果只能来自用户当前有权访问的任务、公告、共享文件和本人个人空间。
- 搜索结果应显示所属小组或个人空间，避免用户将同名文件或任务混淆。
- 已删除、过期、取消分享或失去访问权限的内容不能继续出现在搜索结果中。
- 搜索应在服务端先过滤权限，再返回结果，不能先返回全部数据后由前端隐藏。

### 13.11 数据可靠性与异常处理

- 重要操作需要保证一致性。例如创建任务并分配成员时，要么相关数据全部成功，要么整体失败。
- 文件上传成功但业务记录保存失败时，需要删除无主文件或进入可清理状态。
- 所有提交按钮在请求过程中应避免重复点击，后端也要防止重复请求产生重复记录。
- 删除文件、取消任务、移除成员、转让组长等重要操作需要二次确认。
- 网络中断、上传失败和权限不足时，应显示明确提示，不能将失败操作显示为成功。
- 列表数据需要分页，避免任务、留言、通知和文件数量增加后一次加载全部数据。
- 大文件上传和下载应使用流式处理，避免服务器一次性把完整文件读入内存。
- 系统需要记录关键操作，包括成员变化、权限变化、任务变更、审核结果、文件删除和对外分享。
- 至少需要制定基础备份方案，明确数据库和文件如何一起备份，以及恢复后如何保持引用一致。
- 日志中不能记录用户密码、完整登录凭证、私人文件内容或其他敏感数据。

### 13.12 易用性、兼容性与可维护性

- 状态名称、权限名称和操作按钮应在所有页面保持一致。
- 空任务、空文件库和空通知页面要提供下一步操作指引。
- 文件上传应显示进度或处理中状态，耗时操作结束后给出结果。
- 手机端需要保证表单、上传、任务查看、提交和取件等核心操作可用，按钮和文字不能过小。
- 中文文件名、中文搜索和中文错误提示需要正常显示。
- 权限判断、任务状态变化、文件操作和通知创建应分别封装为统一服务，避免各页面重复实现不同规则。
- 数据库枚举值、后端接口状态和前端显示状态应有统一映射。
- 主要接口和关键数据表需要保留简要说明，便于小组成员协作开发和后期维护。

## 14 隐形需求优先级

| 隐形需求 | 优先级 | 纳入阶段 | 完成判断 |
| --- | --- | --- | --- |
| 不同小组数据隔离 | 必须 | 第二阶段 | 非组员无法通过页面或接口访问小组数据 |
| 服务端权限检查 | 必须 | 第二阶段 | 直接调用无权接口仍被拒绝 |
| 组长唯一和转让规则 | 必须 | 第二阶段 | 转让后始终只有一名有效组长 |
| 任务状态机 | 必须 | 第三阶段 | 不合法状态跳转不能发生 |
| 提交与审核分离 | 必须 | 第三阶段 | 上传成果后进入待审核，通过后才完成 |
| 多人任务完成口径 | 必须 | 第三阶段 | 每名执行者状态清晰，任务总状态计算一致 |
| 提交版本与审核关联 | 必须 | 第三阶段 | 能确认审核针对的具体提交版本 |
| 文件业务归属 | 必须 | 第一至六阶段 | 每个文件可确定所属空间和访问规则 |
| 个人空间与小组空间隔离 | 必须 | 第五阶段 | 组长不能访问成员个人空间 |
| 文件进入任务后独立保存 | 必须 | 第六阶段 | 原个人或临时记录删除后成果仍存在 |
| 下载和搜索权限过滤 | 必须 | 第四阶段 | 无权内容不会出现在搜索或下载结果中 |
| 取件码随机性和有效期 | 必须 | 第五阶段 | 取件码不可枚举，过期或取消后不可领取 |
| 文件大小与存储限制 | 必须 | 第一和第五阶段 | 超限上传被拒绝并给出提示 |
| 重复提交防护 | 应当 | 第三阶段 | 重试不会产生重复任务、提交或通知 |
| 临时文件自动清理 | 应当 | 第五阶段 | 到期文件按规则清理且不影响已保存副本 |
| 关键操作记录 | 应当 | 第六阶段 | 可查询主要成员、权限、任务和文件操作 |
| 基础数据备份 | 应当 | 第六阶段 | 数据库和文件可按照说明备份与恢复 |
| 文件历史版本和回收站 | 可选 | 后续版本 | 不影响第一版核心闭环 |
| 实时聊天与实时推送 | 可选 | 后续版本 | 第一版采用留言和站内通知 |

## 15 AI 功能待商议

AI 功能不纳入当前版本的必须完成项，也不作为现阶段项目完成标准。当前开发应先保证账号、小组、权限、任务、文件和跨设备工具的基础闭环可靠运行。

后期讨论 AI 功能时，需要先确定它解决的具体问题，再决定是否接入。可讨论的方向包括：

- 根据项目目标辅助拆分任务和建议负责人。
- 对小组讨论、公告或任务进展生成摘要。
- 对文件内容建立语义搜索。
- 根据任务提交和截止时间生成风险提示。
- 帮助整理项目总结，但不自动修改任务结果或成员权限。

在决定接入前，需要共同评估：

- 调用哪一种模型或 API。
- 是否需要上传小组文件或私人内容给外部服务。
- 用户是否需要主动确认发送的数据。
- API 费用、调用次数和网络不可用时的降级方案。
- AI 输出是否只作为建议，以及用户如何检查和修改结果。
- 哪些功能能够在课程时间内完成并稳定演示。

AI 功能的基本边界是：不能绕过现有权限读取数据，不能自动授予权限、通过任务或删除文件，不能把不确定的生成内容当作系统事实。确定具体功能后，应另行补充用户需求、接口设计、数据范围和验收标准。
